# The Chat Agent — `#apps/chat`

A chat app that is architecturally an **agent harness**: event-based, tool-driven, extensible by construction. It starts as a simple chatbot but every subsystem (loop, tools, skills, identity, compaction) is an independent chain in `#prompts/apps/chat`, and every capability is a file in the dataverse. Regenerate any piece without touching the others.

---

## Architecture

### Event bus

`window.chatEvents` with `on(name, fn)` / `emit(name, data)`. Events: `user, delta, assistant, tool_call, tool_result, compact, plan, status, error, done`. Renderers are subscribers; the agent loop is a publisher. Nothing in the loop touches the DOM directly — UI is a downstream consumer of events, so new listeners (logging, persistence, alternate renderers) attach without modifying the loop.

### Globals

| Global | Purpose |
| :--- | :--- |
| **`window.chat`** | The raw conversation array. Append-only; compaction never mutates it (view-swap pattern). There is deliberately **no persistence layer** — chat is a global variable. Persistence is a tape trick, not code |
| **`window.agentPlan`** | Current plan object, surfaced in the prompt (inert until the plan tool ships) |
| **`window.agentScratchpad`** | Key-value working memory (inert until remember/recall ship) |
| **`window.stopAgent`** | Set true to halt the loop at the next iteration |
| **`window.chatSummary`** | `{ text, upTo }` — the rolling compaction summary |
| **`window.abortCtrl`** | AbortController for the in-flight streaming request |

### The agent loop (ReAct)

`window.runAgent(text)` runs a while-loop over `fetchAI`. The model replies in one of two formats:

```
<<ACTION: tool-name>>
tool input here
```
or
```
<<ANSWER>>
final response here
```

- `parseAction` / `parseAnswer` are regex parsers over the raw reply.
- An ACTION executes the named tool; its return string is pushed as a user-role **observation** and the loop continues.
- An ANSWER terminates the loop. An *empty* answer is still a valid termination (explicit null check — a falsy-string bug here once caused infinite self-answering).
- Breakers: 7 consecutive errors, or 3 consecutive format failures (after which the raw reply is emitted as the answer, gracefully).

### Prompt assembly (wrapper stack)

`window.buildAgentPrompt()` is layered by wrapper chains, innermost first:

1. **Base**: system-file (via `read`) → localStorage `s` → built-in default
2. **OUTPUT FORMAT rules** + concrete EXAMPLE block + AVAILABLE TOOLS + CURRENT PLAN + WORKING MEMORY
3. **SKILLS** section (chain 8): one-line descriptions only
4. **Identity** (chain 10): `<soul>` / `<user>` files prepended; eager `<context file="...">` blocks; the `[[wikilink]]` rule — *"treat each [[link]] as a file name and load it with the read tool before answering"*

Wrapper house rules: unique capture variable names per wrapper (top-level `var` is a shared global), idempotency flags, never self-call the wrapped name. See the hyperprompting guide §4.

### Streaming fetch

`window.fetchAI(systemPrompt)` — SSE streaming against the configured host, AbortController-backed, messages = `[{role:'system',...}].concat(window.chat)`. Emits `delta` / `assistant` / `done` / `error`.

## Tools

Capability is **structural**: the agent can do exactly what exists under `tools/`, nothing more. Read-only mode = don't ship write/delete. Tool discovery lists files by prefix; the leading `/* */` comment is extracted as the tool's description — the only documentation the model ever sees.

Contract: each file is raw JS, the body of an async function with one string argument `INPUT`, returning a string. Errors are strings, never throws.

Shipped tools (each generated by its own chain in `#prompts/tools/*`):

| Tool | INPUT | Behavior |
| :--- | :--- | :--- |
| **`read`** | `filename` or `namespace#filename` | Reads any file from any namespace; splits the `#` itself (kernel `read` takes key and namespace separately) |
| **`list-files`** | empty, `prefix/`, `ns#`, or `ns#prefix/` | Newline-separated key listing via `keys()` + `IDBKeyRange`; no cap (compaction absorbs big listings) |
| **`write`** | first line = path, remaining lines = content | Creates or overwrites; returns `Wrote N characters to path` |
| **`delete`** | `filename` or `namespace#filename` | Structural `.delete(key)` via `queryDB(tx('readwrite', db))`; checks existence first because IDB delete succeeds silently on missing keys |

**Never "delete" by writing `''`** — empty string is the sync layer's *stub* marker ("not yet fetched"), not absence. The file resurrects on sync and empty reads fall back to the `main` namespace. Deletion is structural or nothing.

A **move** operation needs no tool: it's a *skill* chaining read → write → verify → delete.

## Skills

Markdown files under `skills/` with a `/* description */` header line. Only the one-line descriptions enter the prompt (~50 tokens each); the agent loads a skill body on demand via the `read` tool. Progressive disclosure: the QRx filesystem *is* the skills runtime — no MCP layer, no eager schema dumping.

## Compaction

`compact-threshold` = the model's **total context capacity** in tokens, user-declared (the kernel can't know what model you're pointing at). All numbers derive from it:

| Parameter | Value | Lineage |
| :--- | :--- | :--- |
| Trigger | 80% of capacity | Claude Code fires at ~83.5% with a hardcoded buffer; running hotter leaves no room for the summarizer call itself |
| Chunk size | 40% of capacity | OpenClaw `BASE_CHUNK_RATIO = 0.4` — chunk + instructions + running summary + output always fit in one call |
| Raw tail | ~10% of capacity | The most recent messages kept verbatim so the model retains immediate continuity; mirrors Codex's ~20k-token raw preservation on a 200k window |
| Safety margin | ×1.2 | OpenClaw `SAFETY_MARGIN` — char estimates undercount |
| Token estimate | chars ÷ 4 | English rule of thumb; a real tokenizer can't ship because the model is user-swappable. Imprecision is absorbed by the margin and chunk slack |

Algorithm: map (summarize each 40% chunk) → recursive reduce (merge summaries until they fit) → view-swap: `window.chat` is *temporarily* pointed at `[summary] + [raw tail]` during the next `fetchAI` call, then restored. The raw log is never mutated.

## Persistence model

None, by design. `window.chat` dies with the page. Persistence arrives later as a tape trick — serializing the array into a file is `#chats/260908?x=write(JSON.stringify(chat))`, and restoring is a `read` away. No persistence layer will ever be coded into the app.

## Current limits (honest assessment)

- **Multi-step tasks: yes.** The loop iterates tool calls until ANSWER; multi-hop "list → read → answer" works today.
- **Long-horizon within a session: partial.** Compaction prevents overflow death, but `agentPlan` and `agentScratchpad` are inert — the model's only working memory is the transcript, which compaction steadily compresses.
- **Long-horizon across sessions: no.** No persistence yet (see above).

Planned next chains: memory tools (`remember` / `recall` / `plan` — pending a proper literature pass on agent memory design), per-message edit / delete / rerun buttons (rerun = truncate-and-replay, no undo), save/load chat buttons, and the `move-file` skill.

---

## The north star

Self-hosting: a chat that can create and debug the system it runs on. The harness is the prerequisite — every piece above exists so that "agent, fix your own chain file and regenerate yourself" is a conversation, not a feature.
